# 光擎 SolarRestore Agent 说明书

## 1. 项目一句话介绍

光擎 SolarRestore Agent 是面向全球光伏站点的削峰还原 AI 自动化闭环系统。它不是单次训练一个模型，而是把“生产自动运行、当天问题自动分析、新场景沉淀、数据集重构、模型迭代、灰度评估、版本晋升”串成一套可持续进化的业务 Agent。

## 3. 项目要解决的问题

光伏站点在实际生产中会受到 PCS 限功率、电网或卖电策略、负载侧约束等影响，观测到的 PV 功率会被削平。这样会导致三个问题：

1. 真实发电能力被低估。
2. 下游发电预测、收益分析、运营评估使用了被削峰污染的历史数据。
3. 全球站点规模大，人工逐站排查日志、挑样本和判断模型效果不可持续。

本项目通过 AI Agent 将这些工作自动化：

```text
生产自动运行 -> 日终问题分析 -> 新场景沉淀 -> 样本回流 -> 数据集重构 -> 模型训练 -> 灰度评估 -> 主模型晋升
```

## 4. 系统流程

系统核心流程如下：

1. 数据接入 Agent  
   接入 StarRocks 分钟级功率、MySQL 站点配置、NWP 气象数据，并对齐到 288 个 5 分钟点。

2. 检测/场景 Agent  
   通过聚合初筛和明细复筛识别潜在削峰，判断 PCS、电网/卖电限制、负载侧削峰等场景。

3. 还原 Agent  
   使用深度学习模型还原真实 PV 能力，并支持第一版模型和 10000station 迭代模型并行推理。

4. 下发 Agent  
   将削峰还原结果下发到 Kafka 生产主题。

5. 分析 Agent  
   日终自动汇总参与站点、成功/失败列表、错误归因、削峰比例、场景分布。

6. 进化 Agent  
   将线上问题样本回流，重构数据集，训练新模型，发布到 S3，并经过灰度评估后晋升主模型。

## 6. 线上 StarRocks 数据读取

看板支持直接读取线上 StarRocks 9030 数据。

输入项：

- 日期 dt
- station_id
- 模型名，可空
- 明细行数

示例：

```text
station_id = 2026021600036
dt = 2026-05-22
predict_type = 4
```

统计口径：

```sql
SELECT COUNT(DISTINCT station_id)
FROM sigen_device.pv_prediction_history
WHERE dt = ?
  AND predict_type = 4;
```

单站明细口径：

```sql
SELECT *
FROM sigen_device.pv_prediction_history
WHERE station_id = ?
  AND dt = ?
  AND predict_type = 4
ORDER BY record_time ASC;
```

还原前观测功率来自：

```text
sigen_device.station_statistics_min
```

还原后模型结果来自：

```text
sigen_device.pv_prediction_history.predicted_value
```

当前可视化口径：

```text
还原后功率 = predicted_value * 12
```

多发电量计算口径：

```text
多发电量 = sum(max(还原后功率 - 还原前观测功率, 0)) * 5 / 60
```

单位按 5 分钟功率点积分得到 kWh。

## 8. 第一版模型 vs 10000station 迭代版

看板将两个模型放在同一张图里对比：

- PowerRestorationModel：Restoration 第一版
- PowerRestorationModel_10000station：10000station 迭代版

同图展示内容：

2. Restoration 第一版还原曲线
3. 10000station 迭代版还原曲线
4. 两版模型多发电量 kWh
5. 迭代版相对第一版的净提升或下降

当前页面已将“迭代效果检验”做成独立大图区域。左侧是同一站点、同一日期、同一输入下的三条曲线叠加，右侧是多发电量 kWh 对比和灰度结论。点击图表或“放大迭代效果图”可以查看高清大图。

页面还增加了户用光伏发电和全球化调度的视觉点缀，用于帮助评委快速理解本项目面向的是全球户用/工商业光伏站点的生产级 AI 闭环，而不是单点离线模型实验。

灰度评估原则：

```text
候选模型不是上线后直接替换主模型，而是在同站点、同日期、同输入下与第一版模型并行比较。
如果候选模型指标达标，再晋升为主模型。
如果候选模型在某些站点表现偏保守或异常，则把这些站点回流为高价值样本继续迭代。
```

示例站点在 2026-05-22 的结果：

```text
station_id = 2026021600036
Restoration 第一版多发电量 = 27.2595 kWh
10000station 迭代版多发电量 = 9.1512 kWh
迭代版相对第一版 = -18.1083 kWh
```

这个结果说明：

```text
该站点该日样例中，迭代版模型更保守，不应直接晋升。
该样本应该进入灰度分析和样本回流，用于继续定位候选模型欠还原原因。
```

这正是双模型灰度机制的价值：模型迭代不是靠主观判断，而是靠线上真实数据自动比较。

## 9. 飞书 Agent 交互

系统支持通过飞书与用户交互：

```text
Agent 发起问题 -> 用户点击飞书卡片 Yes/No -> WebSocket 接收回调 -> Agent 根据选择继续执行
```

当前 demo 支持：

- 发送确认卡片
- 模拟用户点击 Yes / No
- 识别重复点击
- 更新卡片状态
- 将交互结果压缩为 Agent 可理解的上下文

飞书 Agent 的价值：

1. 让模型晋升、问题确认、异常处置等动作可控。
2. 让业务人员不需要进入后台系统，也能通过飞书参与闭环。
3. 让 Agent 从“只会回答”升级为“能进入业务流程执行动作”。

## 10. 比赛表达重点

本项目适合「AI 业务赛道」的原因：

1. AI 重构业务流程  
   从人工排查、人工挑样本、人工发版，升级为 Agent 自动闭环。

2. 提升业务效能  
   全球区域按本地时间自动执行，万级站点自动汇总。

3. AI IN ALL  
   AI 贯穿检测、场景判断、还原、分析、进化全过程。

4. 生产级落地  
   已接入 StarRocks、MySQL、Kafka、APScheduler、S3，并可接入飞书交互。

5. 持续进化  
   线上问题不止停留在日志里，而是进入高价值样本池、数据集重构和模型版本迭代。

当前 demo 已实现“高价值样本回流”和“数据集与场景标签重构”两个环节。日终分析 Agent 会把失败问题按数据质量、重复索引、功率缺失、气象缺失、mask 边界、工程契约等桶分流；进化 Agent 会生成样本池版本、训练策略、场景标签和新数据集版本。

可以这样介绍：

```text
光擎 SolarRestore Agent 解决的是光伏业务里的真实生产问题。

当光伏站点受到 PCS、电网、卖电或负载侧约束时，观测功率会被削平，真实发电能力被低估。传统方式只能靠人工看日志、逐站排查、人工挑样本、人工发版，无法覆盖全球万级站点。

我们的方案用 AI Agent 重构整个削峰还原流程。系统每天自动读取线上数据，识别潜在削峰，判断削峰场景，用双模型还原真实 PV 能力，通过 Kafka 下发结果，并在日终自动分析成功率和失败原因。

因此这个项目不是一个模型 demo，而是一套生产级、可监控、可交互、可自进化的光伏削峰还原 AI 业务系统。
```
